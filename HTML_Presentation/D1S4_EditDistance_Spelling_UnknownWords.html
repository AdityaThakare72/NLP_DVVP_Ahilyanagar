Fixing Words: Edit Distance, Spelling and Unknown Words

What do we do with words that are misspelled, rare, or that the model has never seen?

Day 1 · Session 4 of 5 · stage 6 of the pipeline

This session has a clean arc: look at the problem in real data, build a way to measure how close two strings are, use that to repair words, then face the harder problem of words that are not mistakes at all, just unseen. The key habit is to measure before fixing: most rare words are not typos.

By the end of this session you can...

  1. Tell a spelling error from a merely rare or unknown word in real text
  2. Compute the edit distance between two words by hand, using a table
  3. Explain how the table works (dynamic programming) and read the loops that fill it
  4. Build a spelling corrector from candidate generation plus word frequency, and say when it fails
  5. Measure the out-of-vocabulary rate on unseen text, and list ways to cope with it

Objective 1 comes first on purpose. Students tend to jump to "let us spell-correct everything". The data will show that this would be a mistake.

Key fact: classic studies (Damerau, 1964) found that roughly 80% of misspelled words are a single slip away from the intended word. So if we can find all words one slip away from a typo, we have usually found the answer.

The 80 percent figure is the classic finding that motivates the whole approach: search close to the typo. It is a historical estimate on typed text; for modern phone keyboards autocorrect changes the mix. Use it as a motivation, not as a measured fact about our reviews.

Edit distance: count the slips

The edit distance between two strings is the smallest number of single-letter edits (insert, delete, substitute) that turns one into the other.

Worked example: kitten → sitting

EditWhat we doWord now
startkitten
1substitute k → ssitten
2substitute e → isittin
3insert g at the endsitting

Edit distance = 3. Could it be 2? Try. The question is how to be sure that no shorter sequence exists. We cannot try every sequence of edits: the number of possibilities explodes. We need a smarter way.

Let students attempt a 2-edit solution and fail. The word "minimum" is the hard part: showing that 3 works is easy, showing nothing shorter exists needs a method. That method, dynamic programming, is the next slide. Also note that edit distance is symmetric: sitting to kitten is also 3.

The big idea: solve the small problems first

Instead of comparing the whole words at once, compare their beginnings, and build up.

D[i][j] = the edit distance between the first i letters of word 1 and the first j letters of word 2.

For kitten and sitting: D[3][2] is the distance between kit and si. D[6][7] is the answer we want, the whole words.

The two ends are easy (comparing with the empty string)

D[i][0] = iturning i letters into nothing takes i deletions
D[0][j] = jbuilding j letters from nothing takes j insertions

This is dynamic programming in one idea: define a table of subproblems, fill the edges that are obvious, and build the rest from them. The analogy students may like: walking up a staircase where each step depends only on the one or two before it. The next slide shows how each interior cell is built from three neighbours.

Every cell is the best of three moves

To get from first i letters to first j letters, look at the last letter of each. Only three things can have happened last:

Last moveMeaningCost: take this neighbour and add
Deletethe last letter of word 1 is extraD[i-1][j] + 1  (the cell above)
Insertword 1 needs one more letterD[i][j-1] + 1  (the cell to the left)
Substitute or matchlast letters line up, same or differentD[i-1][j-1] + (0 if the letters are equal, else 1)  (the cell diagonally up-left)

D[i][j] = the smallest of the three. Because each of those neighbours already holds the best answer for a shorter pair, the minimum of the three is the best answer for this pair. That is why the table is right.

This is the whole algorithm. Ask students why we can trust each neighbour: it was computed earlier as the best answer for a smaller problem. A cell can never be improved by looking elsewhere because any path to the end passes through one of the three neighbours.

The table as Python: two loops, one line of logic

# build a (len(a)+1) x (len(b)+1) grid of zeros
def edit_distance(a, b):
    D = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]

    # base cases: turning i letters into nothing costs i, and the reverse
    for i in range(len(a) + 1): D[i][0] = i
    for j in range(len(b) + 1): D[0][j] = j

    # fill every inner cell, row by row (i = rows, j = columns)
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            same = 0 if a[i-1] == b[j-1] else 1   # letters are 0-indexed, table is 1-indexed
            D[i][j] = min(D[i-1][j] + 1,          # delete
                          D[i][j-1] + 1,          # insert
                          D[i-1][j-1] + same)     # substitute or match
    return D[len(a)][len(b)]

Why a[i-1]?

Table row i covers the first i letters, so the i-th letter is at position i-1 in Python, which counts from 0.

What the two loops do

The outer loop picks a row, the inner loop walks across it. Each (i, j) visit fills one cell. Rows above and cells to the left are always ready.

This is the notebook code. Spend time on the two loops, the earlier practical was criticised for not explaining loops. Draw the grid on the board and move a finger: outer loop goes down, inner goes across. The number of cells is (len a + 1) times (len b + 1), so the time cost is proportional to the product of the two word lengths.

Why the list comprehension and not [[0]*(n)]*m? The second form copies the same row object m times so changing one cell changes a whole column. Mention it only if asked.

295 strings sounds like a lot but it is nothing: each is checked against a Python set in constant time. The formula for a word of n letters is n + (n-1) + 26n + 26(n+1) = 54n + 25. Duplicates appear because, for example, replacing a letter with itself recreates the original word, and inserting "o" next to an existing "o" gives the same string from two positions. Picking the winner: how close, and how common

Several candidates are real words. Two pieces of evidence decide:

Likelihood: how close?

Is this typo a likely slip from that word? One edit is much more likely than two.

Prior: how common is the word?

Before seeing the typo, how likely was anyone to write that word? "the" is far more common than "tea".

A detective. The typo is the evidence. The detective weighs how well each suspect fits the evidence (likelihood) against how likely each suspect was to be there in the first place (prior).

This is called the noisy channel model: the writer meant a word, and a noisy process (typing) corrupted it. Our job is to guess the original. You will meet the same idea in speech recognition and translation.

The formal statement is: choose the word w that maximises P(w) times P(typo given w). We approximate P(w) by relative frequency in the review corpus and P(typo given w) by a decreasing function of edit distance. The score in the next simulator is log of frequency minus a penalty times the number of edits, which is the log of the same product with an exponential likelihood. The values for teh are real from our corpus.

A working spelling corrector: slide the penalty, watch the ranking

Try the example words. For "gud", set the penalty to 0, then to 4. What does each setting get right and wrong?

Walk through: teh gives "the" at any setting. moive gives "movie". goood gives "good". speilberg gives "spielberg" because the name occurs in the reviews. Now gud: with penalty 0 (pure frequency) the answer is "and", because "and" is within two edits and very common. With a high penalty it becomes "guy" or "god", and "good" never wins, because gud to good is two edits. This is an honest failure case: phonetic slang is not a one-slip typo.

The vocabulary here is built from words seen at least three times in the 2000 reviews. A different vocabulary would give different answers.

Where spelling correction breaks

Real-word errors. "I saw it form the start" is all valid words. The corrector sees nothing wrong. It needs the context (from vs form).

Names and new words. 14 of our 40 rare words were names. "kirstie" is not a typo. A corrector would change it to something common.

Slang and phonetic spelling. "gud" is two edits from "good" and one from "guy", and "guy" is more common. Wrong and confident.

Other languages. Hindi or Marathi typed in English letters ("accha", "mast") looks like spelling errors to an English corrector.

Practical rule: correct only when the word is unknown and there is exactly one close candidate you trust. Otherwise leave the word alone. And always measure whether the correction helped.

Be direct about this: spell correction is a tool that can cause damage. In the notebook we correct the 40 sample words and look at what changes, then count how many corrections were harmful by our own judgement. For sentiment classification it often makes no difference at all, because the typos are too rare to matter.

A cheaper fix for stretched words: squeeze repeats with a regex

"sooooo goood", "yeeeeah": people stretch words for emphasis. No dictionary needed:

re.sub(r"(.)\1{2,}", r"\1\1", text)
(.)any one character, and capture it as group 1 (the brackets do the capturing)
\1a back-reference: the very same character that group 1 captured
{2,}two or more times, so the character occurs three or more times in a row
r"\1\1" (replacement)put back just two copies of that character

sooooo goood yeeeeah → soo good yeeah. Why two copies and not one? English has real double letters (good, see, too). Keeping two preserves them. "soo" and "yeeah" are still unknown words, but fewer different spellings of them exist.

This links to Session 3: the regex brackets create a group and \1 refers back to it. That feature goes beyond what a finite automaton can do in general, a good opportunity to mention that practical regex engines have extras on top of the textbook theory, though this specific pattern can be handled by a larger machine.

Unknown words: what a model meets on new text

We built a vocabulary from 1600 reviews and looked at 400 the model never saw. How much is unknown?

Real numbers: 16.4 percent of the distinct words in the test set are not in the training vocabulary, but those words account for only 1.54 percent of the running text, because they are rare. Click the second button: if we also drop training words seen only once, the unknown share of the text rises to 2.53 percent.

The split is random with a fixed seed and stratified by label. Lesson: the OOV problem is usually small in tokens, but not zero, and every new vocabulary trick changes it. It also gets worse for domains the model was not trained on.

Similarity without a dictionary: share character pieces

Break each word into overlapping pieces of n letters (n-grams). Similar spellings share many pieces. Try the example pairs, then change n.

Take good and goood with n equal 3: pieces #go goo ood od# versus #go goo ooo ood od#: four of five shared, 80 percent. Nothing in this calculation needed a vocabulary, so it also works on words we have never seen. This is the idea behind fastText word vectors (a word vector built from its piece vectors) and behind the subword tokenizers of Day 3.

Compare with edit distance: both measure closeness of spelling. Edit distance gives a count of slips, n-gram overlap gives a quick percentage and works well with large sets.

What the practical does

  1. Load the DataFrame. Build a vocabulary table (word, count) and look at the 15 rarest words and the 15 most common
  2. Pull a random sample of once-only words and sort them into the four groups yourself
  3. Write edit_distance with the two loops, print the table for a small pair, and check it against NLTK on 20 random pairs
  4. Generate all strings one edit away from a typo and check them against the vocabulary
  5. Build the corrector. Test it fairly: take 500 known words, corrupt each with one random slip, and measure how often the corrector recovers the original
  6. Squeeze stretched words with the regex and see how many fewer distinct words remain
  7. Split into train and test, measure the unknown-word rate, and compare character n-gram overlaps

The fair test in step 5 matters: it is the only way to know how good the corrector is, because for real typos we do not know the intended word. We corrupt known words ourselves, so the answer key is the original word.

Common mistakes in this session

"Unknown word means typo." In our sample only 4 of 40 were typos.

Correcting every unknown word. Names and slang get damaged. Correct only when confident.

Off-by-one in the table. Table row i is about i letters, so the letter is a[i-1].

Trusting frequency alone. "gud" becomes "and". Distance and frequency must work together.

Testing on typos you cannot check. Corrupt known words so you know the right answer.

Building the vocabulary from test data. Always from the training split, or the OOV rate is fake.

The last mistake is data leakage, which returns on Day 2 when we build classifiers. Introduce it here in a simple form: the vocabulary is part of the model, so it must come from training data only.

Recap, and the problem we are left with

  • Most rare words are names, rare words and inflections, not typos. Measure before you fix.
  • Edit distance = fewest insertions, deletions, substitutions. A table of prefixes finds it: every cell is the best of three neighbours.
  • A corrector generates words one edit away, keeps the real ones, and ranks by closeness and frequency. It breaks on names, slang, and real-word errors.
  • For unknown words we can ignore, map to UNK, normalise, correct, or use pieces. Character n-grams measure similarity without a dictionary.
