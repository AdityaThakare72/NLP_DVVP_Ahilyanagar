From Words to Numbers: Bag of Words and TF‑IDF

A model can only do arithmetic. How do we turn a movie review into a row of numbers, and which numbers should be big?

Day 1 · Session 5 of 5 · stage 7 of the pipeline

The last session of Day 1 closes the pipeline. Everything so far prepared text; today it becomes a matrix. The arc: first the simplest honest way (count words), then see what that gets wrong (common words dominate, order is lost), then fix the first problem with TF-IDF, then learn how to compare two rows (cosine), then check on real data whether the fancier method actually helps. The last part is deliberately sobering.

By the end of this session you can...

  1. Explain why text must become numbers, and build a document-term matrix by hand
  2. Read every parameter of CountVectorizer and say what it does to the matrix
  3. Compute TF-IDF for a small example step by step, including the length normalisation
  4. Compare two documents with cosine similarity and use it to rank search results
  5. Say what a bag of words forgets, and test on real data whether a fancier representation helps

Objective 5 is the honest one. Students often assume that TF-IDF is "better" than counting. We will measure it and the answer is more nuanced.

What we hold now: for each of 2000 reviews, a tidy list of tokens such as ['plot', 'boring', 'acting', 'bad']. A column of lists.
What a model needs: a table of numbers with one row per review and a fixed number of columns, the same columns for every review.
Today: how do we turn a list of words into a row of numbers, and which numbers should be large?

The handoff from Session 4: lists of words are not numbers. Emphasise "fixed number of columns, the same for every review". A review of 50 words and one of 1,000 words must both become rows of the same length. That requirement drives the whole design.

A model is arithmetic on a table

A classifier multiplies, adds and compares numbers. It cannot multiply the word "boring" by 0.7.

What we haveWhat the model wants
review 1: "a boring plot and bad acting"[ 0, 1, 0, 1, 0, 2, ... ]
review 2: "great acting and a great plot"[ 1, 0, 0, 0, 1, 0, ... ]
review 3: "the plot was not good"[ 0, 0, 1, 0, 0, 1, ... ]

The two rules for a good table: (1) every row has the same length, (2) a given column always means the same thing. If column 5 means "plot" in row 1, it means "plot" in every row.

The numbers on the right are placeholders; we build the real ones in the next slides. Rule 2 is the one beginners miss: if each review is encoded on its own, column 5 would mean different words in different rows and the model would learn nothing.

First idea: give every word a column (one-hot)

Make a list of all distinct words, the vocabulary. Give each word its own column. A word is a row with a single 1.

This describes a word, but we need to describe a review with many words. And with our 39,659 distinct words, every word would be a row of 39,659 numbers with a single 1. Useful as an idea; we need to combine them.

One-hot is the building block. Do not linger. The point is the vocabulary-to-column mapping: the same fixed list of columns for everything. The next slide combines the one-hot rows of all words in a review by adding them up.

Second idea: add up the rows of all the words (bag of words)

A review is a collection of words. Put them in a bag, shake, and count how many of each. Add the one-hot rows of every word in the review.

The sum row is the bag-of-words vector. Pause on the fact that the vector for the review has the same length as the vocabulary, no matter how long the review is. That is how we meet rule 1 from the previous slides.

What the bag forgets

Word order

dog bites man and man bites dog give exactly the same row. So do "the movie was good, not bad" and "the movie was bad, not good".

Negation and context

"not good" becomes one count of not and one count of good. The model sees "good" as if the review were praising.

Meaning of words

"great" and "excellent" are separate columns. The table does not know they are close in meaning. One-hot columns are all equally unrelated.

Length

A long review has bigger counts everywhere than a short one, even when they say the same thing.

Why do we still use it? It is fast, easy to inspect, and works surprisingly well for topics and for sentiment (we measure how well at the end of this session). Later days fix the forgotten parts.

Be clear that these are the limits of the representation, not of the library. Part of today (n-grams) patches the order problem a little. Day 3 (transformers) is about patching all of these properly. Length is handled in this session by normalisation.

The same thing in scikit-learn: CountVectorizer, line by line

from sklearn.feature_extraction.text import CountVectorizer

docs = ["the film was good good fun", "the film was bad",
        "the plot was not good", "great acting and a great plot"]

cv = CountVectorizer()                 # an empty counting machine, nothing learned yet
X  = cv.fit_transform(docs)            # fit: learn the vocabulary. transform: count with it

cv.get_feature_names_out()             # the columns, in order
X.toarray()                            # the sparse result written out as a normal table

fit

Reads all the documents once, tokenizes each, and builds the vocabulary: the sorted list of distinct words, each mapped to a column number.

transform

Reads each document again and, for every token, adds 1 to the cell in the column of that word. Words not in the vocabulary are silently skipped.

Run this live. The printed matrix equals the one we built by hand. fit_transform does the two steps together. X is a sparse matrix, which is why toarray() is needed to see it as a table; the reason is on a later slide. The notebook always inspects the vocabulary_ dictionary and the shape after fitting.

fit on training data only: the vocabulary is part of the model

Right

X_train = cv.fit_transform(train_texts)
X_test  = cv.transform(test_texts)

The vocabulary comes from the training reviews. Test reviews are counted with it. Test words that were never seen are skipped, exactly as they would be in real use.

Wrong

X_all = cv.fit_transform(all_texts)
# then split X_all

The vocabulary (and later the idf weights) has now seen the test reviews. The test is no longer a fair surprise, and the score is too optimistic. This is called data leakage.

From Session 4: the same rule as the out-of-vocabulary measurement. A vocabulary built on all the data hides the very unknown-word problem you want to measure. Day 2 uses this rule every time we train a classifier.

The leakage point is introduced gently. In the notebook for this session the vectorizer is fitted on all 2000 reviews because we are exploring the matrix, not scoring a model. The scoreboard at the end uses a pipeline so that the vectorizer is re-fitted inside each fold. Say this explicitly so students know when it matters.

The real matrix: 2000 reviews by 39,659 words

Each small square is one cell. Look at how many are empty.

This picture shows only 30 rows and the 28 most common content words, the densest corner of the matrix. Even here, many cells are empty. Over the whole matrix, fewer than 2 percent of the cells are nonzero. The red and green row labels are the true sentiment; the pattern is not obvious by eye, which is why we need a classifier on Day 2.

The stats row computes: 2000 times 39,659 is about 79 million cells. Only 666,842 of them are nonzero.

Why the matrix is sparse, and why that matters

  • The typical review uses about 330 distinct words out of 39,659. The other ~39,300 cells in its row are zero.
  • Storing every zero would need 2000 × 39,659 numbers: about 635 MB.
  • A sparse matrix stores only the non-zero cells and where they are: about 8 MB. This is what CountVectorizer returns.
  • Rule of thumb: keep it sparse. Call .toarray() only on a small slice you want to look at.

Common trap: calling .toarray() on a large corpus and running out of memory. Inspect a slice such as X[:5, :20].toarray().

666,842 non-zero cells divided by 2000 reviews gives about 333 per review. The density figure shown on the previous slide is the share of nonzero cells in the whole matrix (0.84 percent). The memory figures assume 8 bytes per cell for the dense version.

A problem with raw counts: the loudest words say the least

Which words does a count matrix treat as most important? The biggest numbers. Look at the real totals over all 2000 reviews:

wordtotal countin how many of the 2000 reviews
the76,5291,999
film9,5171,753
good2,4111,182

spielberg12549

"the" is in nearly every review, so seeing it tells us nothing. "spielberg" is in only 49 and says a lot about what the review is about. Counts reward the first and bury the second.

Stop words help only partly: "film" is not a stop word, yet it appears in 88 percent of the reviews, so it carries almost no information about whether a particular review is positive or negative. We need a principled way to turn down the common and turn up the rare, without a hand-made list.

The idea: a word is informative if it is rare across documents

A witness says: "the suspect has two eyes." Useless, everyone does. Another says: "the suspect has a scar over the left eyebrow." That narrows it down. The clue is valuable in proportion to how few people share it.

Two measures, multiplied:
TF (term frequency): how often the word occurs in this document. A word used 5 times matters here.
IDF (inverse document frequency): how rare the word is across all documents. A word in every document scores low.
TF-IDF = TF × IDF: high only for words that are frequent here and rare elsewhere.

So a word ranks high when it distinguishes this document from the rest. That is exactly what search and classification both need.

Intuition first, formulas on the next slide. A good check question: what is the TF-IDF of "the" in a review? Low, because its IDF is near the minimum, however many times it appears. What is the TF-IDF of a word that appears in one review only? The highest IDF possible.

IDF by hand, using the four tiny reviews

df = the number of documents containing the word. scikit-learn's formula (N = number of documents = 4):

idf = ln( (1 + N) / (1 + df) ) + 1
worddf(1+4) / (1+df)ln of thatidf = ln + 1
the35/4 = 1.250.221.22
good25/3 = 1.670.511.51
bad15/2 = 2.500.921.92
Why the "1 +" parts? The 1 + df in the denominator avoids dividing by zero for a word no document contains. The final + 1 keeps a word that appears in every document at idf 1 instead of 0, so it is not erased completely.

Do one row on the board: the has df 3, the fraction is 5 over 4, the natural log of 1.25 is 0.22, add 1. Students need a calculator or the simulator on the next slide. The log is there to soften the effect: a word half as common does not get twice the weight.

Different books use a plain log(N/df). scikit-learn's smooth version is what we use, so the numbers match what the library prints.

The numbers here are identical to scikit-learn's TfidfVectorizer on the same four reviews; we verify that in the notebook.

Stage 4: shrink each row to length 1 (L2 normalisation)

A 1,000-word review would otherwise have bigger numbers than a 50-word review, only because it is longer.

The recipe

  1. Square each number in the row and add them up.
  2. Take the square root. That is the row's length.
  3. Divide every number in the row by that length.

Row for d2: 0.64 (bad), film 0.51, the 0.41, was 0.41 after normalising. Check: 0.64² + 0.51² + 0.41² + 0.41² = 0.41 + 0.26 + 0.17 + 0.17 ≈ 1.0.

After this, every review is a vector of length exactly 1. Only the proportions between its numbers remain: what the review is about, not how long it is.

Cost: the numbers are no longer interpretable as counts. A weight of 0.64 means "a big share of this review's length", not "it appears 0.64 times".

L2 means the usual straight-line length of a vector (square, add, square root). It is the default norm of TfidfVectorizer, controlled by the norm parameter. The check in the example is approximate because of rounding to two decimals.

Now rows can be compared: cosine similarity

Two documents are similar if their vectors point in the same direction. The angle between them is what counts, not the length.

Two reviews in a 2-word world (count of "good", count of "bad"):
A = (3, 1) and B = (6, 2). B is just A written twice as long.

Step 1 dot product: multiply matching positions and add: 3×6 + 1×2 = 20
Step 2 length of each: √(3²+1²) = 3.16, √(6²+2²) = 6.32
Step 3 divide: 20 / (3.16 × 6.32) = 1.00

Cosine 1.0 means same direction. 0 means nothing in common. The straight-line distance between A and B is 3.2, which would call them "far apart". Cosine correctly says they say the same thing.

The result of exactly 1.00 comes from A and B pointing in exactly the same direction. For word counts, which are never negative, cosine runs from 0 to 1. After L2 normalisation every vector has length 1, so step 2 is skipped and cosine is just the dot product. That is why TfidfVectorizer plus a dot product is how search engines rank in their simplest form.

Cosine vs straight-line distance: move the vectors

Try the first button, then drag one slider at a time. Which number changes when you only change the length of a review?

First preset: same direction, B twice as long. Cosine stays 1.00 while the distance is large. Second preset: all the weight on "good" for one, all on "bad" for the other; cosine is 0. Ask students to find sliders that give cosine 0.5. This is the key behaviour that makes cosine the right tool for comparing documents of different lengths.

Patching word order a little: n-grams

Switch between 1 word and 1+2 words. See what happens to "not good".

With pieces of 1 and 2 words, "not good" becomes its own column, separate from "good". The model can now learn that this pair tends to appear in negative reviews. The price: the vocabulary explodes. On the 2000 reviews it goes from 39,659 columns to 538,909 with bigrams, because almost every pair is rare. With min_df=3 it comes back down to 81,480.

The red tokens in the output mark pairs that begin with not or no, as a visual aid; the vectorizer itself does not know which pairs matter.

How to read that table honestly

Most gaps are noise

The spread across folds is 1 to 2 points, and 2000 reviews is a small collection. Differences below about 2 points should not be trusted. Only "binary" stands apart, and even that is one experiment.

A plausible reason for binary

Sentiment is mostly about which words appear ("awful", "wonderful"), not how many times. Counting repeats can overweight one long rant. This is a hypothesis; we have not tested it here.

TF-IDF is not a free upgrade

It was designed for ranking documents against queries. For classification it can help or not, and it interacts with the classifier's own settings (Day 2).

The habit to keep

Do not assume the more complex representation wins. Build a small scoreboard like this one, with cross-validation, and let the numbers decide.

This is the integrity slide. We do not claim a mechanism we have not tested, so the explanation for binary is marked as a hypothesis. With 5 folds of 400 reviews each, the accuracy of a single fold has a standard error of about 2 points by itself (the square root of 0.83 times 0.17 over 400). Hence the caution about small differences.

Also mention that all runs used default classifier settings, so a different regularisation strength could shift TF-IDF rows. Day 2 covers tuning.

Common mistakes in this session

Fitting the vectorizer on test data. Use fit_transform on train, transform on test.

Calling .toarray() on everything. 635 MB for 2000 reviews. Look at slices.

Mixing up the two axes. Rows are documents, columns are words. Shape is (documents, words).

Assuming TF-IDF is always better. Measure it. Here it was not.

Vectorizing the query differently. A search query must use the same fitted vectorizer, or the columns do not line up.

Comparing by straight-line distance. Long reviews look far from short ones. Use cosine, or normalise.

The fifth mistake is the same rule as leakage in reverse: anything that becomes a vector must go through the same fitted vectorizer. Rule 2 from the start of the session, a column always means the same word.

Recap, and what Day 2 starts with

  • A model needs a table: same row length, and every column always meaning the same word. The bag of words gives that by counting.
  • Counts forget order and meaning, and the loudest words say least. TF-IDF down-weights words found in many documents; L2 normalisation removes the effect of length.
  • Cosine similarity compares two rows by direction, which is what ranks search results.
  • On real data, a fancier representation did not automatically win. Measure with cross-validation.
Still unsolved, and Day 2 starts here: we now have a matrix X (2000 × 39,659) and a label for each row, y (positive or negative). How does a program learn from X to predict y? What does "83% accuracy" really promise, and how do we check it is not fooling us?

The handoff to Day 2: statistical NLP and machine learning. The matrix X and the label vector y are the two inputs of every classifier we meet tomorrow: Naive Bayes, logistic regression and others. The accuracy question previews evaluation and cross-validation, which we used today as a black box.
