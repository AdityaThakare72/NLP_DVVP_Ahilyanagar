Where we are

From Session 2: AutoModel gives a 768-number [CLS] vector for any text. It encodes the text, but it is not a sentiment score: nothing in pretraining asked BERT about positive or negative.

What we have

A pretrained BERT (110 M weights), 50,000 labelled IMDB reviews, 9,613 labelled SST-2 sentences, and the Day 2 baselines.

What we want

A model that says positive or negative, and evidence that it is better than TF-IDF with logistic regression, which reached about 90% on IMDB in practical B6.

Remind students of the B6 numbers: about 89.7% baseline and 92% after tuning on IMDB. A transformer has to beat that clearly to be worth the GPU time.

Transfer learning: reuse what was learned

A doctor spends years on MBBS (general knowledge of the body), then a few months on a specialisation. Nobody re-learns anatomy for each specialisation. Pretraining is the MBBS; fine-tuning is the specialisation.

Feature extraction

Freeze BERT. Compute the [CLS] vector of every review once, then train logistic regression on those vectors.

Cheap, needs no GPU for training. Weaker: BERT's vectors were never shaped for sentiment.

Fine-tuning

Add a small layer and train all weights, BERT included, on our labels, with a small learning rate.

The standard approach and what B7 asks for. Every layer adjusts a little towards the task.

Feature extraction is a useful middle step for students without GPU access, and the notebook shows it. The BERT paper reports that fine-tuning beats feature-based use on most tasks, though the gap is small for some.

From Day 2, Session 1: the head is logistic regression (a weighted sum plus softmax) on the [CLS] vector. The difference: during fine-tuning, the 768 numbers it reads are themselves being improved.

The library prints a warning that some weights were newly initialised (the classifier); that is expected, not an error. Tell students before they see it in the notebook. num_labels=77 would give a 77-way intent classifier with the same code.

Cross-entropy

−log P(correct label). P = 0.9 costs 0.11; P = 0.1 costs 2.3. Confident mistakes are punished hardest.

Gradient

For each of the 110 M weights: which direction lowers the loss. Computed by backpropagation through all 12 layers.

Epoch

One pass over the training set. 4,000 reviews in batches of 16 = 250 steps per epoch.

From Day 2, Session 1: the same "walk downhill" as logistic regression, just with far more weights. AdamW adapts the step size per weight and adds weight decay (a gentle pull towards zero, like regularisation).

Cross-entropy values: -ln(0.9) = 0.105, -ln(0.1) = 2.303. The Trainer runs this loop for us; the notebook also shows the five lines of a manual loop once, so the Trainer is not a black box.

Hyperparameters that matter

settingtypical for BERTwhat goes wrong otherwise
learning rate2e-5 to 5e-5too high: pretrained knowledge is destroyed, loss jumps; too low: nothing changes in 2 epochs
epochs2 to 4more epochs on small data: training accuracy near 100%, test accuracy falls (overfitting)
batch size16 or 32larger batches run out of GPU memory on Colab
max_length128 to 512too short cuts the opinion off; 512 is 4× slower than 256 per layer of attention
warmup, weight decay10% of steps, 0.01without warmup the first random head gradients can shake BERT's weights

The BERT paper's advice: batch size 16 or 32, learning rate 5e-5, 3e-5 or 2e-5, and 2 to 4 epochs. Pick by the validation score, never the test score (Day 2, Session 2).

The learning rate for fine-tuning is about 50 times smaller than for training a small model from scratch (next slide uses 1e-3). The pretrained weights are already good; we only want to nudge them.

The learning rate, seen in real training runs

A small transformer (2 layers, 128-number vectors) trained from scratch on SST-2, here on a CPU. Three learning rates, same everything else.

Real runs. Too low: the loss falls slowly and dev accuracy lags. Too high: the loss stays near 0.69, which is -ln(0.5), the loss of guessing 50/50: the model learned nothing. Note how dev accuracy peaks and then falls while training loss keeps dropping: overfitting, which is why we keep the best epoch by dev accuracy. For BERT the same picture holds around 2e-5 instead of 1e-3.

Long reviews: how much is cut off?

Token counts use our 8,000-piece IMDB tokenizer from Session 2; BERT's larger vocabulary gives somewhat fewer tokens per review, so treat these as upper estimates. Even so, at max_length 256 over 40% of reviews lose text, and at 512 still about one in seven. The question is then which part to keep.

Which part of a review carries the verdict?

Experiment: our TF-IDF + logistic regression model (from B6) trained on full reviews, tested on only 128 words of each test review.

The end of a review is more informative than the beginning: people describe the plot first and give the verdict last. Keeping a little of the start and more of the end is best.

The same finding for BERT: Sun et al. (2019), "How to Fine-Tune BERT for Text Classification?", got their best IMDB results keeping the first 128 and the last 382 tokens.

Real numbers on the 10,000 IMDB test reviews. The "head+tail" row keeps the first 32 and the last 96 words. The B7 notebook implements head+tail truncation in a few lines on token ids, and students can compare it with the default (head only).

Our datasets for B7

IMDB (50,000 reviews)

Long reviews, 2 balanced classes. Fine-tuning on all 25,000 training reviews takes too long on a free GPU, so B7 samples a few thousand for training and 2,000 for testing (a setting you can raise).

SST-2 (Stanford Sentiment Treebank)

Short movie-review sentences: . The dev and test sentences are the same ones GLUE uses; GLUE's training set also includes 60,000+ phrases.

SST-2 is harder per item (one sentence, often subtle: "it's not that it's bad, it's just not funny") but quick to train on. IMDB gives the model more text per item but needs truncation.

Our SST-2 copy is the sentence-level split of Socher et al. (2013) from a public GitHub repository, so it loads without a Hugging Face login and has labelled test sentences (GLUE hides its test labels).

Fine-tuning with the Trainer, line by line

from transformers import TrainingArguments, Trainer
args = TrainingArguments(
    output_dir="bert-imdb",              # where checkpoints are saved
    learning_rate=2e-5,                 # small: nudge the pretrained weights
    per_device_train_batch_size=16,
    num_train_epochs=2,
    weight_decay=0.01, warmup_steps=warmup,  # warmup = 10% of all update steps
    eval_strategy="epoch",               # score the validation set after every epoch
    save_strategy="epoch", load_best_model_at_end=True,
    metric_for_best_model="f1",
    fp16=True, report_to="none")       # half precision on the GPU; no logging service
trainer = Trainer(model=model, args=args,
                  train_dataset=train_ds, eval_dataset=val_ds,
                  compute_metrics=compute_metrics)    # our function: accuracy, precision, recall, F1
trainer.train()
trainer.evaluate(test_ds)

No GPU? Then training BERT-base on thousands of reviews takes hours. In Colab: Runtime → Change runtime type → T4 GPU, before running anything.

eval_strategy was called evaluation_strategy in older versions of transformers; the notebook uses the new name. load_best_model_at_end keeps the epoch with the best validation F1, which protects against the overfitting seen in the learning-rate runs.

Evaluate exactly as on Day 2

def compute_metrics(eval_pred):
    logits, labels = eval_pred                     # raw scores (n, 2) and true labels (n,)
    preds = logits.argmax(axis=-1)                 # the class with the larger score
    p, r, f1, _ = precision_recall_fscore_support(labels, preds, average="binary")
    return {"accuracy": accuracy_score(labels, preds), "precision": p, "recall": r, "f1": f1}

How much does pretraining buy? SST-2 test accuracy

A transformer trained from scratch on 6,920 sentences does worse than TF-IDF: the architecture alone is not the magic. The gain comes from pretraining on billions of words.

Published BERT numbers are on GLUE's test server with GLUE's larger training set; your B7 number on our split will be in the same region, not identical.

Rows marked "this deck" were computed for these slides on the 1,821 SST-2 test sentences. The BERT rows are from Devlin et al. (2019, GLUE test) and Sanh et al. (2019, DistilBERT, SST-2 dev). Ask students to add their own B7 result as a final row.

Where fine-tuning breaks

Small data, many epochs

110 M weights can memorise a few thousand examples. Watch validation scores, stop early.

Domain shift

A model fine-tuned on movie reviews is weaker on tweets or product reviews (B6 showed the same for TF-IDF).

Cost and speed

A GPU to train, and prediction is far slower than logistic regression. For many business tasks TF-IDF is good enough.

Bias and opacity

Pretraining text carries social biases into predictions, and we cannot read 110 M weights the way we read B6's word weights.

The honest summary for students: use a transformer when the extra accuracy matters and you can afford the compute; always keep the simple baseline as a reference.

Case study: classifying customer support queries

The task

"I was charged twice for my card payment" → duplicate_charge. Route each message to the right team.

BANKING77 is a public dataset of 13,083 banking queries in 77 intents.

What changes from sentiment

num_labels=77 instead of 2, labels mapped to ids, and macro F1 (average over classes) because small intents matter as much as big ones.

Same tokenizer, same model, same Trainer, same metrics. That is the point of pretrained transformers: a new classification task is a new dataset and one changed number.

This is the case study named in syllabus Unit IV. It also connects to deployment (Session 5): a fine-tuned classifier is typically served behind a REST API that receives a message and returns the intent with a confidence.

Common mistakes in this session

Training on a CPU runtime. Check the GPU first: torch.cuda.is_available().

Learning rate of 1e-3 for BERT. The loss sticks at 0.69 (guessing). Use 2e-5.

Choosing epochs by test accuracy. Use a validation split.

Comparing on different test sets. Score the baseline on the same sample.

Labels as strings. The model needs 0/1 integers in a column called labels.

Running out of GPU memory. Lower the batch size or max_length, use fp16.

The "labels" column name matters: the Trainer passes it to the model, which then computes the loss itself.

Recap, and what Session 4 starts with

  • Fine-tuning = pretrained BERT + a 768 → labels layer, all weights trained with a small learning rate for 2 to 4 epochs.
  • Long texts are truncated; for reviews keep the end.
  • Evaluate with the Day 2 metrics on a held-out test set, against a baseline on the same items.
  • The gain comes from pretraining, not from the architecture alone.
Still unsolved: BERT outputs labels. What if the output should be text, such as a summary of a long news article? Session 4: encoder-decoder models BART and T5 that write, and ROUGE to score what they write.

1. Count new weights

BERT-base head for 5 classes: how many new weights?

768 × 5 + 5 = 3,845.

2. Steps

6,000 training reviews, batch 16, 3 epochs. How many update steps?

6000 / 16 = 375 per epoch; 1,125 in total.

3. Loss

The model gives the true class probability 0.5. Cross-entropy?

−ln 0.5 = 0.693: the value of a model that is guessing.
